# Mirror pages

The plan `mirror-plan` prints: the Mirror database's fixed schema and one page per Problem, derived only from the Practice Log. Build the same plan by hand when you have no shell. The Practice Log schema is the `leetcode-tutor` skill's `references/practice-log.md`.

## Contents

- The plan
- Database
- Page properties
- Page body
- Writing values through a connector

## The plan

```json
{
  "database": {"id": "...", "title": "...", "description": "...", "key": "Problem ID", "properties": [...]},
  "pages": [{"properties": {...}, "body": "..."}]
}
```

`database.id` is `mirror.notion_database_id` from `practice-log.json`, or `null` before the first push. `pages` holds one page per Problem folder, sorted by folder path (`problems/<source>/<slug>/`).

## Database

- **Title:** `Practice Log`.
- **Description:** `One-way Mirror of the Practice Log at <repository>, generated by LeetCode Tutor. Edits made here are overwritten on the next push.`
- **Properties,** in this order:

| Property | Type | Options |
| --- | --- | --- |
| Problem | title | |
| Problem ID | text | |
| Difficulty | select | Easy, Medium, Hard |
| Tags | multi-select | every Tags value in the pages, sorted |
| Lists | multi-select | every Lists value in the pages, sorted |
| Need Review | checkbox | |
| Need Review Reason | text | |
| Attempts | number | |
| Last Attempt | date | |
| Last Outcome | select | solved-alone, solved-with-hints, saw-solution |
| Link | url | |
| GitHub | url | |
| Pending | checkbox | |

In the plan, the `options` of Tags and Lists hold the sorted, de-duplicated values the pages use (Lists names differing only in case are one option, see below) (an empty list when none use any). `Problem ID` is the key a push matches pages by. `Pending` marks an Attempt written straight to the Mirror from a chat platform, in the format of the `leetcode-tutor` skill's `references/chat-platforms.md`; the plan leaves it unchecked on every page.

## Page properties

`<repository>` is `mirror.repository` as `https://github.com/<owner>/<repo>`, and `<folder>` is the Problem's folder, `problems/<source>/<slug>`.

| Property | Value |
| --- | --- |
| Problem | `title`, or the Problem ID when it is empty |
| Problem ID | `<source>:<slug>`, from the folder |
| Difficulty | `difficulty` capitalised (`Easy`); empty when it is none of `easy`, `medium` and `hard` |
| Tags | `tags`, lowercased, de-duplicated and sorted |
| Lists | `lists`, in the notes' order, once each; names differing only in case are one list, spelt as the first Problem folder (in path order) writes it |
| Need Review | `need_review` is `true` |
| Need Review Reason | `need_review_reason` when Need Review is set, otherwise empty |
| Attempts | the number of Attempts in the log |
| Last Attempt | the latest Attempt `date`; empty when there is none |
| Last Outcome | the `outcome` of that Attempt (on a tie, the later one in the log); empty when it isn't one of the three outcomes |
| Link | `link`; empty when it has none |
| GitHub | `<repository>/tree/HEAD/<folder>` |
| Pending | unchecked |

Notion's limits: a text or title value longer than 2000 characters is cut to its first 1999 and `…`, and a comma in a Tags or Lists name becomes `;` (`graph, bfs` → `graph; bfs`), since select options can't hold commas.

## Page body

Markdown, with a blank line between blocks:

```markdown
> Generated from [this Problem's notes](<repository>/tree/HEAD/<folder>) in the Practice Log. Edits made here are overwritten on the next push: change the notes in the Practice Workspace instead.

## Key Takeaway

<the notes' Key Takeaway, as written, or "None yet.">

## Attempts

### <the Attempt's heading, as written>

- Mode: <mode>
- Outcome: <outcome>
- Approach: <approach>
- Mistakes: <mistakes>
- Language: <language>
- Code: [<code>](<repository>/blob/HEAD/<folder>/<code>)
- Origin: <origin>
```

One `###` block per Attempt, in the log's order, each leaving out the lines whose field is empty. So `Mistakes: none` means none were observed, and no Mistakes line means they aren't known. With no Attempts, the section holds `No Attempts yet.` instead.

## Writing values through a connector

Turn each value into what your Notion connector expects: text and urls as strings, a select as its option name, a multi-select as its option names, a checkbox as checked or unchecked, `Attempts` as a number and `Last Attempt` as a date (`YYYY-MM-DD`, no time). An empty or `null` value clears the property. Write the body as the page's content, replacing everything on the page.

Notion's connector rejects a multi-select value that isn't already one of the property's options (`Invalid multi_select value for property "Tags"`), and a new database starts with no Tags or Lists options. So before writing any page, make the data source's options cover the plan:

1. Take the `options` of Tags and Lists from `database.properties` (without a shell, collect every value the pages use).
2. Fetch the data source for the options it already has. A new database has none.
3. When some are missing, call `notion-update-data-source` once with `ALTER COLUMN "Tags" SET MULTI_SELECT('a', 'b'); ALTER COLUMN "Lists" SET MULTI_SELECT('c')`, listing every existing option plus the missing ones, since options left out are removed. Escape a single quote in a name by doubling it. Leave a property alone when nothing is missing.

Do this on every push, not only the first: a later push can bring new tags or lists. Never remove an option the data source already has.
